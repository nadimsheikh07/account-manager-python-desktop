# Account Manager Agent

**Project**: Account Manager Python Desktop Application  
**Type**: PyQt-based desktop accounting and inventory management system  
**Primary Focus Areas**: User Management, Account Ledgers, Product/Inventory, Purchase/Sale Orders

## Project Overview

This is a Python desktop application for comprehensive account management, featuring:

- **Authentication & User Management**: User login, roles, and account creation
- **Account Management**: User accounts with financial ledgers and transactions
- **Product Management**: Product catalog, categories, pricing, and stock tracking
- **Order Processing**: Purchase orders and sale orders with detailed line items
- **Dashboard**: Charts and analytics for users and financial data

## Architecture

```
src/
├── models/          # Data models (User, Product, Purchase, Sale)
├── services/        # Business logic and database operations
├── controllers/     # Request handlers for views
├── views/           # UI components organized by feature
└── components/      # Reusable UI components (sidebar, heading)

config/             # App configuration (database, theme, UI)
utils/              # Utilities for forms and PDF generation
```

## Key Patterns & Conventions

### MVC Flow
- **Model** → **Service** → **Controller** → **View**
- Services handle database queries; controllers bind data to views
- Product flow example: `models/product.py` → `services/product.py` → `controllers/product_controller.py` → `views/product/`

### Data Models
- Models defined in `src/models/` with fields and relationships
- Product model includes `price` and `cost` fields (keep synchronized across views/forms)
- Each model typically has a corresponding service for CRUD operations

### Services Layer
- Database operations in `src/services/`
- ORM conversion (to/from dict) handled in controllers
- Key services: `dbSetup.py`, `auth.py`, `user.py`, `category.py`, `product.py`, `productStock.py`, `purchaseOrder.py`, `saleOrder.py`, `userAccount.py`, `userLedger.py`

### Views Structure
- Features organized by domain: `auth/`, `product/`, `purchaseOrder/`, `saleOrder/`, `userAccount/`, `user/`
- Subdirectories for entity types: `categories/`, `products/`, `productStocks/`
- Typical view files: `index.py` (list view), `form.py` (create/edit form), `detail.py` (single record view)

### Forms & Input
- Form utilities in `utils/formUtils.py`
- Field validation and data binding handled in forms
- Controller methods typically `_orm_to_dict()` for data conversion

## Common Tasks

**Adding a new feature**:
1. Define model in `src/models/`
2. Create service in `src/services/`
3. Create controller in `src/controllers/`
4. Create views in `src/views/{feature_name}/`

**Working with products**:
- Keep `price` and `cost` synchronized across model, controller, service, form, and list views
- Reference: Product stock operations in `productStock.py` and related views

**Database setup & migrations**:
- Use `src/services/dbSetup.py` for database initialization
- Schema defined through model definitions

**PDF generation**:
- Utilities available in `utils/pdfUtils.py`

## Known Conventions

- Controllers use `_orm_to_dict()` method for model-to-dict conversion
- Services handle direct database operations and ORM queries
- Views import and use controllers to fetch/display data
- Authentication handled through `src/services/auth.py` and `src/controllers/auth_controller.py`

## Configuration

## Entry Points

## Tips for Assistance

When working with this project:
- Reference the MVC flow and architecture patterns
- Verify data field synchronization (especially for Product price/cost)
- Check both service and controller implementations when fixing bugs
- Ensure form fields match model fields
- Test dashboard calculations against the ledger services
